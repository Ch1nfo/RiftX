# ADR 0002: v0.8 Legacy OS Guard

- Status: Accepted
- Date: 2026-07-25
- Decision owners: RiftX maintainers
- Relates to: [ADR 0001](0001-v0.7-local-native-execution.md)

## Context

ADR 0001 described Native / Hardened / Auto with Hardened and Auto fail-closed on platform RiftX Guard readiness. v0.8 product direction renamed modes to RedTeam / Pentest / Auto and moved enforcement to application-layer approval policy, Kill Switch, and audit. Shipping was blocked when Guard was unavailable on operator machines.

`riftxd` already activates engagements without Guard preflight and starts agent threads with `hardened: None`. `GatewayState` no longer carries a `PlatformGuard`.

## Decision

1. OS Guard is **legacy** for v0.8. It is not on the product feature schedule.
2. Mode safety is expressed as:
   - RedTeam / Pentest / Auto naming and approval mapping (`UnlessTrusted` / `Never` as documented).
   - Auto lab + expiry + confirmation phrase.
   - Operator Pause / Kill Switch.
3. The `codex-riftx-guard` crate may remain for experimental spawn/env helpers (`apply_hardened_launch`, network policy env encoding). Callers must not treat Guard readiness as a gate for mode activate.
4. Full-library case encryption and `.riftxcase` packaging remain non-goals for the v0.8 “good enough” release; existing engagement-record cipher usage may stay without expanding the product narrative.
5. Linux-first TUI remains out of schedule for this release.

## Consequences

- ADR 0001 items that require Guard fail-closed for Hardened/Auto are **superseded** for product behavior.
- Removing the entire Guard crate is deferred while credentials/PTY/adapter still reference launch helpers; dead gateway wiring is removed instead.
- New work must not reintroduce “Guard unavailable → refuse mode” on the desktop/daemon path.

## Supersedes (partial)

ADR 0001 decision points about Hardened Mode requiring platform Guard and Auto depending on Guard for start readiness, relative to v0.8 shipping criteria.
