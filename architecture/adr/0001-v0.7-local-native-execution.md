# ADR 0001: v0.7 Local Native Execution

- Status: Accepted (partially superseded by [ADR 0002](0002-v0.8-legacy-guard.md) for OS Guard fail-closed behavior)
- Date: 2026-07-23
- Decision owners: RiftX maintainers

## Context

RiftX must support professional red-team workflows on macOS, Windows, and Linux without requiring Docker, Podman, Kubernetes, or a remote worker. It must provide three explicit execution modes:

- Native Mode gives the operator direct local tool execution with authorization checks and audit.
- Hardened Mode adds the platform-specific RiftX Guard and stronger policy enforcement.
- Auto Mode runs an authorized objective without supervision, but only in a Lab environment and with an authorization expiry, Scope, audit, snapshots, Guard, and a kill switch.

The repository previously contained a container-oriented execution path. The product decision explicitly removes container and remote execution, so retaining that path would preserve the wrong architecture and continue to shape new work around obsolete interfaces.

## Decision

1. RiftX will reuse the vendored typed Agent Runtime for conversation, turns, model events, approvals, interruption, and tool orchestration.
2. Product-facing components, configuration, and interfaces use RiftX terminology. Upstream names remain only where required for source attribution and internal compatibility.
3. The target execution path is local on the operator host:

   ```text
   Desktop or CLI
     -> local IPC
     -> riftxd
     -> Agent Runtime
     -> Native Executor or RiftX Guard
     -> local Tools and Skills directories
   ```

4. Product IPC uses a Unix domain socket on macOS/Linux and a named pipe on Windows. It does not expose a TCP listener.
5. The container manager, remote environment, container exec path, and fixed dynamic security tools are deleted without a compatibility period.
6. Native shell, PTY, stdin, interruption, artifact collection, approval, audit, recovery, and kill-switch behavior will be implemented and tested directly against the local architecture.
7. Execution modes are introduced first as validated domain contracts. Native Mode and Auto Mode must not be exposed through a public API or UI until their enforcement and lifecycle semantics are implemented.
8. Auto Mode is rejected unless the engagement environment is `lab` and the authorization has an expiry. Optional runtime budgets do not replace these mandatory controls.
9. Secrets remain in the operating-system credential store. Agent state, prompts, audit records, reports, and command-line arguments contain references and grants only.
10. Linux, macOS, and Windows CI must validate shared domain and serialization contracts before platform executors are added.

## Consequences

- Native execution provides the freedom expected by professional operators and makes all three operating systems first-class targets.
- Hardened and Auto security claims depend on platform-specific Guard implementations and cannot be declared complete based only on application-layer checks.
- There is a single local execution architecture; development cannot fall back to the removed container path.
- Internal upstream crate names may remain during migration, but they are not part of the RiftX product surface.

## Removed Legacy Surface

The following surfaces are intentionally not supported:

1. Docker, Podman, Kubernetes, VM, or remote-worker execution backends.
2. A manager daemon for container lifecycle or network namespaces.
3. Remote Agent Runtime environments and container exec sessions.
4. Fixed `rt_*` dynamic tools or preinstalled penetration-testing binaries.
5. Compatibility APIs or data fields that exist only for the removed execution path.
